# Secrets and configuration

> Part of the [2026 campaign record](README.md). Status: design, started September 2026.

[Index](README.md) · [Strategy](strategy.md)

## Intent

A person, a CI job, and a cloud agent apply configuration the same way, from one list of what exists. Production credentials are hard to end up with on a laptop or an agent VM. Adding a variable means updating one list that local setup, CI, and deploy are all checked against.

## Starting point (2026)

[ENV.md](../../ENV.md) describes the intended flow. Each package loads dotenv. `.env` is gitignored and `.env.template` is committed. Production values come from GitHub Actions secrets and CDK stack outputs at deploy. Development values are supposed to come from the team 1Password vault through `op inject`.

In practice:

- `op://` references exist in the API and client templates, but only the client defines the inject script (`npm run env:dev`). Other packages (`data-tables-handler`, `ai-data-analyst`, `infra`, `spatial-uploads-handler`) have their own templates — some empty, filled by copying from a neighbor.
- The API's variable surface (`packages/api/process-env.d.ts`) spans Auth0, Postgres, Redis, R2, SES, Mapbox, Cloudflare Images, Lambda ARNs, and SQS queues. The client bakes a second set of `REACT_APP_*` values in at build time.
- Workflows name secrets job by job (schema drift, client build, client preview, deploy). Nothing fails when a new variable is missing from a workflow.
- Several development values are production credentials or production resource names: the production Auth0 tenant including its Management API client, R2 keys, bucket names, Lambda ARNs, and queue URLs. [Auth0](auth0.md) is the sharpest case, because those credentials can update production users.
- The API already has one hard guard: `resolveTilesAclNamespace` refuses to run outside production without `TILES_ACL_NAMESPACE`, and refuses the value `prod`. Nothing like it covers the other variables.

The many `.env` files are a symptom. The gap is that no one has classified which values are public configuration, which are shared development secrets, and which must never leave production.

## Classes

Every variable has exactly one class. The class decides where a value may appear.

| Class | Examples | Laptop / cloud agent | CI | Production |
| --- | --- | --- | --- | --- |
| Public config | Ports, local GraphQL URL, log level | Committed defaults | Committed defaults | Deploy config |
| Shared development secret | Non-production Auth0 application and management client, Mapbox development token, snapshot **read** key | 1Password, or the agent platform's secret store | Only in jobs that need it. Smoke CI needs none of the Auth0 values | Absent |
| CI secret | `E2E_TEST_MODE` shared secret | Optional, for running journeys locally | GitHub environment for CI | Absent. The API refuses test mode in production |
| Production secret | Production Auth0 client secret, production R2 write keys, production Lambda ARNs, SES credentials | Absent | Absent, except in the deploy workflow | GitHub production environments and CDK |
| Per-environment name | Bucket names, `TILES_ACL_NAMESPACE`, SQS queue URLs, `CLIENT_DOMAIN`, database URL | A development value, never production's | An isolated value | The production value |

The test for "production secret" is effect, not convenience. A value that can mutate production data, invoke a production Lambda, or consume a production queue is a production secret, however it has been used locally. A token that cannot mutate SeaSketch data (a Mapbox public token) may be a shared development secret. Public, immutable reference objects (for example the published WoRMS parquet files) are read by URL without credentials.

Queue URLs are per-environment names for a specific reason. The API's overlay-engine consumer receives and then deletes messages. A development API pointed at the production queue would take production report results away from production.

## Design

**One committed manifest.** A single file lists every variable: its name, class, which packages read it, which profiles require it, and a short description. `process-env.d.ts`, the client's env typings, `.env.template` files, the deploy workflow, and `GraphQLStack` are consumers of that list. A check in CI fails when a consumer names a variable the manifest does not, or the reverse. [ENV.md](../../ENV.md)'s checklist becomes "add it to the manifest."

**Named profiles.** Variables are the schema. Values live in named profiles: non-production (laptops, CI, agents, staging) and `seasketch.org` production. Adding another production profile is a data change, not a schema change ([second production install](second-install.md)).

**Generated dotenv files are a cache.** `.env` stays gitignored, generated by one root command from 1Password for people. CI and cloud agents do not need the files when the environment is already populated. `.env` stays the delivery format in development because that is what every package already loads.

**Existing injectors, no new product.**

| Consumer | Injector |
| --- | --- |
| Developer laptop | 1Password CLI through one root command that writes each package's `.env` |
| GitHub Actions | GitHub environments, with jobs declaring the manifest profile they need instead of hand-picked secret lists |
| Cloud agent | The platform's secret environment. The agent runs the same root commands, never opens 1Password interactively, and never depends on a shell profile |
| Production | Unchanged: GitHub production environments plus CDK |

**Fail closed.** `npm run setup` and API startup refuse to run outside a production deploy when any production-class value, or a production per-environment name, is present. `resolveTilesAclNamespace` is the model: a small check in code, not a review convention. The list of forbidden values is profile data for the `seasketch.org` install, not a hardcoded belief that only one production exists.

## Sequencing

**Phase 1** puts on the manifest only what the core profile, snapshot pull, and `E2E_TEST_MODE` need, with non-interactive injection for CI and agents and 1Password for laptops. Snapshot **push** credentials are maintainer-only and absent from every default profile.

**Before phase 3** moves CI and agents onto the data path, every variable in the API and client typings is classified, and the default non-production profile cannot write to production. Mutable storage moves to development buckets and queues ([local services](local-services.md)).

Production deploy keeps working throughout. The manifest grows by describing variables that already exist. It does not require rotating every production secret on one day.

## Decisions

- The manifest is the single list, and CI checks that its consumers agree with it.
- Values are named profiles, not a fixed dev/prod pair.
- `.env` remains the development delivery format. Only how it is produced and what it may contain change.
- `REACT_APP_*` names stay until the client build replacement (phase 4). The manifest records them as build-time client config, so they can be renamed in one pass.
- Human login uses a non-production Auth0 tenant. Automated tests receive no Auth0 credentials. ([Auth0](auth0.md), [integration testing](integration-testing.md))

## Open questions

- *(Phase 1)* Manifest format (YAML or a typed module) and location.
- *(Phase 1)* Whether CI and laptops share one read-only snapshot key or use two.
- *(Phase 1)* How the production-value check identifies values on day one: an explicit list of known production identifiers, or a comparison against the production profile.

## Exit criteria

- **Phase 1:** A clean VM obtains core configuration without a shell profile. CI has the snapshot and test-mode secrets and nothing else it does not use. Setup refuses a production tile ACL namespace and production Auth0 identifiers.
- **Before phase 3:** Every API and client variable is in the manifest with a class. The non-production profile cannot write to production storage or consume production queues. [ENV.md](../../ENV.md) describes the manifest instead of a per-package checklist.
- **Phase 4:** Client build-time variable names change once, from the manifest, with the new bundler.
